# Klukai's own Redis (aichat decoupling, step 1): recovery plan

## Data preserved

This compose change adds Klukai's own Redis, `companion-redis` (valkey pinned
by digest, password from `KLUKAI_REDIS_PASSWORD` in the encrypted compose env,
append-only file on the `companion-redis` volume, no published port) and
points core and the events bridge at it instead of the aichat stack's Redis.
Factual memory moves from the aichat data service into core, which now reads
and writes the same `memory` table rows itself: no row is moved, rewritten or
deleted, and no migration is added. Redis holds only rebuildable state (rate
limits, caches, session scratch, the `companion:events` channel); the few
keys in aichat-redis db 1 are copied with their TTLs before cutover, and the
source keys are left in place.

Before release keep: `SELECT count(*) FROM memory` and the `companion:%`
subset, the deployer's restore-verified dump under
`/mnt/nvmeINT/backups/klukai/releases/`, and the pre-decouple dump
`/mnt/nvmeINT/backups/klukai/aichat-pre-decouple-20261027T143947.dump`.
Counts must never decrease.

## Rollback

The aichat network and `DATA_URL` stay in this release, so the previous image
starts with the new compose file and still reaches every aichat service it
used (its Redis URL now names `companion-redis`, which it accepts). No
migration was added, so the previous image starts against the current
database.

Automatic: the deployer re-pins the previous image and recreates core.
Manual: pause deploy-on-merge, pin the previous image
(`~/.local/state/klukai/release/core-image.json` from the rollback tag) and run
`python3 ops/amarillo/scripts/klukai_compose.py up -d --no-build --no-deps companion-core`.
To return Redis to aichat as well, check out the previous compose file
(commit before this change) in the production checkout and recreate
`companion-core` and `events-bridge` the same way; aichat-redis is untouched.
Leave `companion-redis` and its volume in place; never delete it while a core
points at it.

## Verification

`docker inspect companion-core` shows `REDIS_URL` naming `companion-redis`;
`/health` and `/ready` are ok with `redis: ok`; the bridge logs a subscription
to `companion:events`. `memory` counts equal the pre-release counts, and a
recall of a known `companion:<user>:rel:*` fact returns the same value as
before. Run `scripts/e2e_live.py` as the `claude` test user. A packet capture
on the aichat bridge shows no new connection from core or the bridge to
aichat-redis or aichat-data.
